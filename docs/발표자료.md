## 1. 문제 정의 (Before)

기존 이에이포스 홈페이지는 다음과 같은 문제를 안고 있었습니다.

| 영역 | 문제 |
|---|---|
| **성능** | 첫 화면에 약 **134MB** 다운로드. 비정상 비트레이트 영상 2개(각 66·65MB)가 **동시에** 버퍼링 |
| **콘텐츠** | 텍스트 정보 거의 0 → 회사·제품·연락처를 알 수 없음, 검색 노출·신뢰도 취약 |
| **접근성** | 스크린리더 대응·키보드 조작·대체텍스트 전무, 버튼 라벨이 "CLICK" |
| **공유** | 카카오톡·슬랙 공유 시 미리보기 이미지 **깨짐**(존재하지 않는 파일 참조) |
| **버그** | 문의 모달이 페이지 전체를 **자기 자신으로 재로딩**하는 치명적 결함 |
| **브랜드** | 실제 브랜드(스틸블루)와 충돌하는 네온민트 버튼 |

→ **"있긴 한데, 느리고·비어 있고·신뢰가 안 가는" 상태.**

## 2. 우리가 한 일 (After) — 5대 축

### ① 성능 최적화 — 가장 강력한 성과
- 영상 재인코딩 + 스트리밍 최적화(faststart), 이미지 적정 해상도 리사이즈.
- 화면 크기에 맞는 영상 **1개만** 내려받도록 동적 로딩 → 불필요한 67MB 차단.

> **134MB → 6.6MB, 약 95% 감축.** (= 4G에서 수십 초 → 수 초)

### ② 신뢰도·콘텐츠 강화
- **회사 정보·연락처 섹션 신규** 구축: 사업 소개, 핵심 제품(고순도 용매추출제 등), 전화·이메일 **클릭 연결**, 주소, 사업자등록번호.
- 검색엔진 구조화 데이터(JSON-LD)·사이트맵으로 **검색 노출 기반** 마련.

### ③ 접근성(웹 표준) 확보
- 시맨틱 구조·대체텍스트·키보드 포커스·모달 표준 대응(ESC·포커스 트랩).
- "장애인·모바일·검색봇 모두가 읽을 수 있는" 사이트로.

### ④ 브랜드 디자인 시스템
- 색·여백·타이포를 **디자인 토큰**으로 체계화 → 일관성·유지보수성 확보.
- 브랜드 스틸블루 적용, 히어로 태그라인, 스크롤 인터랙션 등 **완성도 있는 인상**.

### ⑤ 연구데이터 분석 대시보드 (차별화 포인트)
- 폐배터리 재활용 연구데이터를 **추출 효율·회수 구성·용매 성능** 차트로 시각화.
- 데이터 파일만 교체하면 자동 반영되는 **확장형 구조**로 설계.

- **렌더 블로킹 제거(약 2.1초 단축)**: 웹폰트를 비차단 방식으로 로드.
- **색 대비(접근성 96→100)**: 본문 보조 텍스트·링크 색을 WCAG 기준 충족하도록 상향.

## 4. 기술적으로 내세울 포인트 (질문 대비)

- **빌드 없는 순수 정적 구조 유지** — 프레임워크·번들러 없이 nginx에 바로 서빙. "운영 단순성"이라는 의사결정.
- **불필요한 다운로드 차단** — `matchMedia` 기반 조건부 미디어 로딩.
- **지연 로딩(lazy-load)** — 차트 라이브러리를 초기 로딩에서 분리해 첫 화면 속도 보존.
- **확장형 데이터 파이프라인** — 분석 결과(JSON) → 대시보드 자동 반영. 분석/표현 레이어 분리.
- **웹 표준·접근성(WCAG) 준수** — 단순 미관이 아닌 품질 기준 충족.
- **before/after를 Git 히스토리로 증명** — 초기 상태 커밋 → 개선 커밋으로 변화량 추적 가능.

## 7. 예상 질문 & 답변(준비)

**Q. 디자인만 바꾼 것 아닌가요?**
> 핵심은 성능입니다. 자산을 95% 줄여 실사용 로딩을 수십 초→수 초로 단축했고, 접근성·SEO·데이터 시각화까지 품질 전반을 끌어올렸습니다.

**Q. 대시보드 데이터는 실제인가요?**
> 현재는 구조 검증용 샘플이며, 실제 연구데이터 수신 시 파일 교체만으로 반영되도록 **파이프라인을 먼저 완성**해 둔 상태입니다.

**Q. 왜 프레임워크를 안 썼나요?**
> 운영 환경(nginx 정적 서빙)에 맞춘 의사결정입니다. 빌드 없이 바로 배포되어 운영이 단순하고 안정적입니다.
